# 三高産業 ハウスEC(プロトタイプ)

ビニールハウス・パイプハウスの資材販売と施工のためのECサイト試作版です。
中心は **ハウスカルテ**(お客様ごとのハウス台帳)と **3Dハウスシミュレーター** で、
「担当者が訪問時にハウスを登録 → お客様はスマホで自分のハウスを見る → 張り替え・修理・新設の見積りをその場で依頼」
という流れを一通り動かせます。

サーバー不要の静的サイトなので、このリポジトリの GitHub Pages でそのまま公開できます。
公開URLの例: `https://<ユーザー名>.github.io/<リポジトリ名>/mitaka-ec/`

## デザイン方針「暁(あかつき)」

ベンチマーク(Bootstrap Farmer、Johnny's Selected Seeds、Greenhouse Megastore、食べチョク、坂ノ途中、北欧暮らしの道具店、Snow Peak、Aesop、土屋鞄、Tesla/IKEA/meviy の構成体験)を調べたうえで、次の方針で作っています。

- 色は「深緑黒 #0B1F16 × 朝焼け #E8622A」の2色対比。緑を面に塗らない。ダーク面は感情(ヒーロー・カルテ・フッター)、明るい面は**純白の「図面の紙」**(極薄の方眼を地にだけ敷き、カードは白。方眼の有無と1pxの線だけで面の差をつける)。ベージュは使わない。棚の6色は面でなく線(左バー・見出し文字)に使う。
- 書体は見出し Zen Old Mincho、本文 BIZ UDPゴシック(UD設計)。数字は等幅。
- 写真は使わず、実時間3D(`house3d.js`)と線画SVGで画をつくる。トップのヒーローは3Dのハウスに朝6時の低い光を当て、**時刻スライダー**で太陽・空・影が動く。スクロールで外観→軒下→内部へカメラが寄る。
- 角丸は 4 / 12 / 18 / 999 の4段、明るい面では影を使わず1pxの線。動きは 160/240/420/900ms。
- 農業らしさは、朝の光、赤城山の稜線(面の境界の罫線)、二十四節気の帯(最上部)、土色の下線だけで出す。
- 70代向けは「文字を大きく」だけに頼らず、行間1.75、コントラスト4.5:1、タップ56px、農家の言葉(「被覆資材」→「張る」)で対応。

カタログの設計方針は「絵で選ぶ資材棚」です。商品より先に注意書きを置かない、品番はカード表面に出さない、文字は15px以上・ボタンは56px以上、13分類は6つの棚に束ねる、数量は −/+ で入力させない、を守っています。
| `scripts/import-catalog.mjs` | 販売管理の商品マスタ(CSV)から `catalog-data.js` の商品を生成 |
| `supabase/schema.sql` | 本番DBのテーブル定義(customers / plots / houses)と図鑑用ビュー |
| `vendor/three/`, `vendor/qrcode/` | three.js r180、QRコード生成(いずれもMIT)。CDNに依存せず動くよう同梱 |

## 使い方(プロトタイプ)

1. `staff.html` を開き、担当者コード(初期値 `1234`、`config.js` で変更)で開く。
2. 「デモデータを入れる」を押すと、お客様3名・ハウス6棟のサンプルが入る。`karte.html?c=DEMO01` で見られる。
3. 訪問先では、お客様 → 圃場(現在地をピン) → ハウス(複数棟は「この棟を追加」) → 同意 → 「登録してカルテを発行」。
4. 発行されたQRコードを読み取る、またはURLをLINEで送ると、お客様が自分のカルテを開ける。
5. カルテの「張り替えを見積る」「修理・相談」「3Dで見る」から、見積依頼やシミュレーターにつながる。

ブラウザ保存モードでは、登録した端末のブラウザにだけデータが残ります(社内テスト用)。
複数の担当者・お客様で共有するには次の「本番運用の前にやること」の 1 を行います。

## 顧客管理(このプロジェクトの本体)

ECは表側で、裏の本体は顧客管理です。**入力を仕事の副産物にする**ことを最優先に設計しています。

### 何がどこに残るか

| 接点 | 自動で残るもの | 担当が5秒で残すもの |
|---|---|---|
| 訪問(カルテ登録) | お客様・圃場・ハウス・同意・位置・写真、訪問した記録 | 状態と一言メモ |
| **電話(いまの主流)** | ― | 番号でお客様を出す → 用件を押す → 話した内容(声で入力可) → 次にすること |
| EC(見積依頼) | 見積(quotes)・接点ログ・お客様(初めての方は仮登録) | 後から担当が状態を進める |
| EC(行動) | 商品を見た / かごに入れた / 3Dで作った / 見積を依頼 / カルテを見た の5種だけ | ― |

マウスの動きや広告IDのような、業務に使わないものは取りません。

### 災害モード

台風・大雪のあと、**どこから回るか**を集めたデータから出します。登録しておくと順番を待たせない、という農家さんへの約束を、実際に果たすための画面です。

- 災害の種類(台風・大雪・雹・強風)と地区を選ぶと、対象のハウスが**弱い順**に並びます。弱さは「要補修 / 張り替え時期 / 耐雪補強なし / 長い棟」で決め、大雪のときは耐雪なしの重みを上げます。
- 圃場が地図にピンで出ます。色はその圃場でいちばん重い被害、数字は棟数。押すと一覧の該当行に飛びます。
- 現場では被害を**1タップ**(被害なし / 軽微 / 大きい / 倒壊・全損)。記録すると `house_events` に残り、大きい被害は「要補修」に変わって翌日期限のやることが立ちます。
- **記録中は並び順が動きません**。押し間違いを防ぐためで、並べ直しは明示的なボタンで行います。
- 被害の記録から**必要になりそうな被覆材**を集計します(全損は全面、大きい被害は4割として概算)。巻数の目安まで出るので、そのまま発注の判断に使えます。
- 未確認の棟の**連絡リスト**をコピーできます。お見舞いと安否確認の電話に使います。

### 「今日やること」は入力させずに出す

溜まったデータから自動で作ります。見積の依頼、提出から7日返事のないもの、被覆材の張り替え時期が来たハウス、電話メモで決めた折り返し。担当者が朝いちばんに見る画面です。

### データの形

`supabase/schema.sql` が本番のテーブル定義です。検索・集計・権限の軸になる項目は実の列にし、3D構成と取込原文だけ jsonb に置いています。

- **customers**: お客様コード(口頭用6桁)と**カルテトークン(URL用32桁)を分ける**。6桁は総当たりできるため。重複は物理削除せず `merged_into_id` で統合。
- **houses / house_components / house_events**: ハウスを会社の資産台帳として持つ。担当者が辞めても残る中心。
- **interactions**: 電話・LINE・訪問・FAXの接点ログ。追記型(消さずに足す)。
- **quotes / quote_items**: 3D構成のスナップショットと**単価版**を必ず残す。単価改定後も過去の見積を再現できるように。
- **consents**: 目的別に、いつ同意をもらったかを追記型で。目的は `karte`(カルテ作成・お知らせ。必須)、`stats`(個人がわからない集計)、`share_ja`(**JA・提携する資材店・メーカーへの提供**)、`showcase`(事例掲載)、`line_push`(LINE配信)。

  `share_ja` は**1人目の登録から取ります**。後から「やはりJAにも見せます」となったとき、登録済みの全員に取り直すのは現実には不可能なためです。断った方は外すだけで済みます。お客様には「断っても当社のサービスは今までどおり使える」と必ず伝えます(登録画面に読み上げ文があります)。提供する項目と提供しない項目は `privacy.html` に明記しています。

  なお、会社や事業ごと譲り渡す場合(事業譲渡)は、この取り扱いを引き継ぐことを条件に情報も引き継げます。`share_ja` が効いてくるのは、事業譲渡ではなく**データを見せる・貸す**場合です。
- **ec_events / tasks / attachments / products / audit_log**。

**金は販売管理が正、関係と資産はCRMが正**。双方向同期はしません(得意先マスタの二重更新は必ず壊れるため)。CRMは `sales_system_code` を持つだけにします。

### 権限(ここを間違えると全顧客の電話・住所が漏れる)

- 担当者: Supabase Auth でログインした人だけが読み書き。
- お客様: テーブルには触れず、`rpc_get_karte(token)` 1本だけで自分のカルテを読む。
- EC訪問者: 行動ログの追加と見積依頼の作成だけ。読み取り不可。

試作の旧版は「誰でも全部読める」設定でした。本番前に必ず新しい `schema.sql` を適用してください。

### 溜まっているかを測る

担当者コンソールの「溜まり具合」に出しています。お客様数、登録ハウス数、30日の接点ログ、動いている見積、電話番号あり率、張った年あり率、電話の重複、1年以内に更新した割合。**接点ログが増えないときは、入力が面倒になっている合図**です。

### 進め方

1. **0〜3か月**: 新スキーマとRLS、電話メモ、見積のDB化。運用は電話ログと見積から始める。
2. **3〜6か月**: LINE連携(カルテのQRでIDを結ぶ)、やることの自動生成、施工ジョブ、販売管理の夜間CSV取り込み。
3. **6〜12か月**: EC行動と連動した追いかけ、災害モード、商品2万点のDB化、JAとの共同利用の枠組み。

## 本番運用の前にやること

1. **データベースをつなぐ**: Supabase でプロジェクトを作り、`supabase/schema.sql`(v2)を実行し、URLと anon キーを `config.js` に入れる。担当者ログイン(Supabase Auth)を有効にする。
2. **写真を写真置き場(Storage)に移す**: 試作は端末内に画像を持っています。本番ではStorageに上げ、DBには場所だけ残します(`attachments`)。
3. **LINEをつなぐ**: LINE公式アカウントの友だち追加URLを `config.js` に入れる。お知らせ配信(張り替え時期・災害前点検)は Messaging API で後から追加。
4. **単価を差し替える**: `pricing.js` の `UNIT` と `OPTIONS.films[].perSqm` を自社単価に。`PRICING_VERSION` も更新。
5. **商品マスタを取り込む**: 販売管理から CSV を出し、`node mitaka-ec/scripts/import-catalog.mjs 商品マスタ.csv`。列の形式は `scripts/sample-products.csv` を参照。約2万点でも動くが、商品数が数千を超えたら検索とページ送りの改善を行う。
6. **見積依頼の送信先**: `config.js` の `mailTo` と、用意できれば `quoteEndpoint`。
7. **会社情報・同意文面**: フッター、`quote.html` の連絡先、`privacy.html` の文面を確定する。
8. **公開設定**: 各ページの `<meta name="robots" content="noindex">` と「プロトタイプ版」バナーを外す。

## メーカー品のデータについて

佐藤産業・誠和・東都興業の商品は、公開されている商品名・用途をもとに「雰囲気を出すため」に入れたものです。
規格と価格は確認前の参考値(または要見積)なので、正式運用では商品マスタからの取り込みに置き換えてください。

## 概算見積りの計算方法(概要)

- アーチは「垂直の脚 + 半楕円」でモデル化し、弧長をラマヌジャンの近似式で求めています。
- アーチ本数 = 奥行 ÷ アーチ間隔 + 1。母屋の本数は間口で 3・5・7 通りに切り替わります。
- 被覆材面積は屋根・側面・両妻面の合計に 10% のロスを加えています。
- 施工費は床面積 × m²単価 + 基本料。張り替えのみは被覆面積 × 単価 + 基本料 + 旧フィルム処分。
- 運搬費は地域で固定額(その他地域は別途見積り)。消費税は 10%。

## 今後の拡張候補

- 注文・決済(掛け払いの請求書発行、カード決済)と注文履歴のカルテ反映
- LINE通知(張り替え時期、台風・降雪前の点検、災害時の優先受付)

- 写真からの部材特定(LINEで写真を送ると担当者が見積りを返す)
